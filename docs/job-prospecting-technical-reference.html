01 · System shape

Architecture & data flow

Two orchestrator skills (offer and cold) share a single infrastructure and both delegate their CV-preparation preamble to one internal sub-skill. Two satellite skills operate over the shared SQLite database — one writes, one reads. All shared code (scripts/, schemas/, config/, references/) physically lives inside job-application-tailor; every other skill points at it via SKILL_BASE_TAILOR rather than copying.

Design principleTruthfulness first. A layered guardrail system (§9) ensures no generated artefact can assert a skill, title, or metric that isn't traceable to the master CV or the user's cv_addendum.md. The database and generation layers are deliberately separated so verification stays honest.

Delegation contract

Both orchestrators Read job-prep-cv/SKILL.md for Steps 0–2.5, passing $FLOW (offer|cold), $INPUT_SEED, and $EARLY_BLACKLIST_NAME. The sub-skill runs scripts/preflight.py and hands back resolved paths ($PROJECT_ROOT, $SKILL_BASE_TAILOR, $OUTPUT_DIR, $PREP_DIR), the loaded $CUSTOMIZATION, and a verified $PREP_DIR/cv_fact_base.json. Control returns to the orchestrator at Step 3.

03 · Offer flow

End-to-end pipeline

The offer flow (job-application-tailor/SKILL.md) runs ~10 steps. Steps 6 & 7 execute as two parallel Agent subagents; the fit gate at Step 4 can halt the run before any document is generated.

0–2.5

CV preparation (delegated)

Handed to job-prep-cv: dependency & master-CV checks, folder creation, customization load, and the cache-hot path of fact-base extraction/verification.

→ cv_fact_base.json (cached, hash-keyed)
3

Analyse the job offer

URL HEAD-probe → WebFetch (with a "preserve original language, do NOT translate" guard) → LLM extraction. Detects language; runs the platform-vs-client (aggregator) check.

→ job_offer_analysis.json, raw_offer.md
3.5

Duplicate & history check

One-shot check-duplicate wrapping the 3 duplicate layers (exact-URL, company+title, fuzzy >80% skill overlap), same-company context, and a blacklist lookup. Exit 1 stops.

3.6

Research the company

Foreground WebSearch for size, news, culture, tech-stack, and key contacts (with LinkedIn URLs). Skippable via behaviour.skip_company_research.

→ company_research.md (with ## Contacts)
4

Match / gap analysis + fit gate

Per-requirement direct / transferable / gap matrix → overall_fit_pct. Deterministic recount, schema-validate, grounding check, fit-level folder rename. Halts if fit < 50%.

→ match_analysis.json
5

Tailor the CV

Company-size-aware re-emphasis with an earlier-experience compression cutoff; the addendum is merged in-memory only. Forbidden-title-label invariant enforced.

→ tailored_cv.json
6·7

Letters & LinkedIn (parallel agents)

Subagent 1: motivation letter → short letter. Subagent 2: LinkedIn messages using real contact names. All schema-validated; orchestrator waits for both.

→ letter.json · short_letter.json · linkedin.json
8

Interview prep (foreground)

Likely questions, talking points, company context, and a fit-score banner — generated in the foreground (no background agent).

→ interview_prep.md
9

Generate output files

generate_outputs.py: schema-validate → DOCX/PDF/TXT + responsive interview-prep HTML + run summary.

→ *.docx / *.pdf / *.txt / *.html · run_summary.json
10

Record in job history

Insert company / title / skills / fit / output-folder into job_history.db for future duplicate detection and stats.

04 · Speculative flow

How the cold flow differs

Steps 0–2.5 are identical (delegated). The middle of the pipeline diverges — there's no job description, so there's nothing to score.

Replaces Step 3

Company research

Builds company_profile.json from the site, Indeed MCP, LinkedIn, and news. Defaults to French. Canonicalises the folder slug.

Adds

org_type classification

Tags the org end_employer / esn / staffing_agency / recruitment_agency / unknown. Load-bearing: every downstream prompt reframes for intermediaries.

Replaces Step 4

Target-role inference

infer_target_role.md proposes candidates → stack-grounding check → interactive user pick (never auto-selected) → selected_role.json.

Replaces fit score

Company dossier

company_dossier.md (→ HTML). Its "Why you / why them" section is a narrative angle of approach instead of a numeric fit score.

The cold flow's worst tellFor an intermediary you'd be placed on a client's mission or represented to an employer — so the pack is a "here's the profile I offer" letter, not a "your mission moves me" letter. Writing the wrong one is the giveaway org_type exists to prevent.

Cold rows record source='cold' with org_type and a company_profile_snapshot, leaving offer-only scoring columns NULL and job_skills empty. --supersede retires a prior live row for the same company + role when re-prospecting.

05 · Command surface

The CLI — cli.py

Single entry point: python scripts/cli.py <subcommand> [options]. The history database is resolved automatically (JOB_TAILOR_HOME → legacy repo resources/ → OS app-data dir); --db <path> overrides it. Besides the DB commands, the CLI carries the pipeline-support subcommands the skills call between steps (probe-url, cache-raw-offer, detect-platform, rename-with-fit, rename-cold-folder, check-forbidden-labels, save-cv-cache) and a timeline trend report. Subcommands are defined declaratively in the scripts/commands/ registry (one module per domain) — the parser, the dispatch table, and the pre-mutation backup set all derive from it, so they cannot drift apart. build_parser() is the canonical source of truth — the reference at references/cli.md is auto-generated from it and drift-checked by a pre-commit hook.

07 · Persistence

The job-history database

A single SQLite file — resources/job_history.db (git-ignored), schema v3. All access is funnelled through JobHistoryDB, which never edits the canonical file live (see the resilience note below).

applications — one row per pack

ColumnTypeConstraints
idINTEGERPK AUTOINCREMENT
company_nameTEXTNOT NULL
company_normTEXTNOT NULL · indexed
job_title / job_title_normTEXTNOT NULL
location · source_url · domain · seniorityTEXT—
fit_levelTEXT— (very_good/good/medium/low)
fit_pctREAL—
direct_count · transferable_count · gap_countINTEGER—
output_folder · detected_languageTEXT—
statusTEXTNOT NULL DEFAULT 'generated' · indexed

org_typeTEXTnullable · added v3

created_at · updated_atTEXTNOT NULL · ISO-8601

Companion tables: job_skills (FK → applications(id) ON DELETE CASCADE; skill_type CHECK in required/preferred), company_lists (PK company_norm; list_type CHECK in blacklist/whitelist), and a single-row schema_version.

Controlled values

status:generatedappliedinterviewofferrejecteddropped
source:offercold
org_type:end_employeresnstaffing_agencyrecruitment_agencyunknown

Enum enforcement is application-level (Python ValueError), except skill_type / list_type which carry SQL CHECK constraints. dropped rows are excluded from all duplicate checks.

Migrations — automatic, idempotent

  • v1 → v2: adds source (DEFAULT 'offer' backfills existing rows) and company_profile_snapshot.
  • v2 → v3: adds nullable org_type — legacy/offer rows stay NULL; only the cold flow populates it.
  • Runs on every open: _init_schema reads MAX(version) and only ALTER TABLE ADD COLUMN for absent columns. Uses its own schema_version table, not PRAGMA user_version.

3-layer duplicate detection

LayerMatch onReason string
1 · Exact URLsource_url = ?"exact URL match"
2 · Company + titlecompany_norm AND job_title_norm"same company + job title"
3 · Fuzzy skillssame company, Jaccard skill overlap ≥ 0.80"same company, N% skill overlap"

Normalisation aliases keep matching robust: c#→csharp, .net→dotnet, javascript→js, typescript→ts.

Resilience — network/mounted FS safeJobHistoryDB operates on a temp-dir mirror keyed by a sha1 of the DB path, under a cross-process advisory lock, and only _sync_back()s to the canonical file at init and close — integrity-checked with PRAGMA integrity_check before and after os.replace, retrying 4×, never overwriting a healthy target with a corrupt copy. compute_content_fingerprint (SHA-256 over sorted row tuples) lets doctor detect silent replacement or a stale restore.

08 · Source of truth

The CV fact base

A structured extraction of everything true about the candidate — resources/cv_fact_base.json, validated against schemas/cv_fact_base.schema.json (Draft 2020-12). Every downstream artefact must ground in this file.

Top-level fields

candidate_name*headlinecontactcandidate_location summaryskillstechnologiestechnologies_to_deepen methodologiesexperience*projectseducation languagesconstraintstransition_signals

* required. experience[] items carry type (role|training), details, and metrics. technologies_to_deepen is kept separate so tailoring never lists still-being-learned tech as a core skill.

Cache keyed on the CV hash

# .cv_hash holds the SHA-256 of MASTER_CV.docx (8192-byte chunked) cv_cache_is_valid(cv_path) → cv_fact_base.json + .cv_hash exist AND stored_hash == file_hash(cv_path)

When the CV changes, the hash no longer matches and preflight emits status: cache_stale — the signal to re-extract (Steps 1–2.5), not to hand-refresh the hash.

09 · Truthfulness

The guardrail system

Four checks, wired into preflight, a pre-commit hook, and the cache-write path — defense-in-depth against shipping a claim the CV doesn't support.

CheckWhat it enforcesSeverity
factbase_consistency.pyEvery salient metric (a number carrying +, %, or PB/TB/GB) in the fact base still appears in the CV. Bare ints & years ignored. --check-hash compares .cv_hash.blocks (exit 1)
verify_fact_base.pytechnologies & methodologies must appear literally in the CV; skills are warnings; metrics reuse the drift check.blocks / warns
check_match_grounding.pyA direct match whose tech token isn't in the fact base is a false-direct (inflates fit). Tech tokens block; soft-skill phrases warn.blocks / warns
common.save_cv_fact_base()Runs the drift check before writing .cv_hash and raises on drift — re-blessing a stale fact base by hand is impossible.raises
The incident these closeThe master CV was updated 40+ → 100+ applications while the fact base still said 40+. Verification at the time only checked tech/methodology presence — not numbers — so stale data shipped. The metric-drift check now makes that a blocking failure, wired into preflight, the cache-write gate, and the pre-commit hook.

The offer and cold grounding checks (check_match_grounding.py, check_role_grounding.py) import a shared _grounding_common.py so their synonym maps and tokenizers can never diverge.

10 · User layer

Customization — addendum & prefs

Two optional user-owned files (both git-ignored) let the toolkit know true-but-off-CV facts and personal preferences, without ever mutating the verified cache.

cv_addendum.md

Three recognised sections

  • ## Additional experience entries → bullets attached to an existing role (matched by company + dates)
  • ## Hidden skills → addendum_hidden_skills
  • ## Off-CV facts to remember → addendum_off_cv_facts
user_prefs.yaml

Honoured keys

  • preferred_title_labels / forbidden_title_labels
  • tone_directives
  • team_context_companies
  • default_language (default auto)
The critical invariantmerge_addendum_into_fact_base() returns a new dict and never mutates the cache. Addendum bullets attach to experience[].details only — never to technologies/methodologies — which keeps verify_fact_base.py honest. The addendum enriches the run without corrupting the hash-keyed cache.

Two invariant checkers back the prefs: find_forbidden_title_label_violations (whole-word match against the tailored CV title) and find_team_context_solo_phrasing (flags "solo / only developer / seul développeur" near a team-context company mention).

12 · The fit gate

Fit scoring

Each offer requirement is classified, then a single percentage decides whether the pipeline proceeds.

direct transferable gap
# common.recount_match_summary — deterministic, run before validation overall_fit_pct = round( (direct + transferable * 0.5) / total * 100 ) # empty matches → 0
Hard gate

50% or stop

Below overall_fit_pct = 50 the run halts before CV tailoring. The match analysis and renamed folder are kept.

config/settings.default.yaml

Fit levels

very_good ≥ 85 · good ≥ 70 · medium ≥ 50 · below = low. Maps pct → folder prefix.

A dry-run / score-only mode (behaviour.dry_run, or "just the score" in the request) stops after match analysis — fit score only, no CV or letters — while still recording the application.
